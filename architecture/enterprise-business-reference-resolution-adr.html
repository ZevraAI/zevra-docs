Enterprise Business Reference Resolution

How Zevra resolves a user's free-text reference to a specific enterprise entity — a product, supplier, store, warehouse, customer, employee, purchase order, invoice, or promotion — to its canonical row before planning begins, as a natural extension of the existing semantic grounding pipeline.

§0

ADR summary

Decision

Business Reference Resolution becomes a new step inside AgentBrain.resolve(), positioned immediately after its existing BusinessLanguageResolver.resolve() call. It uses one new, generic, retrieval-only contract — modeled on the existing, already-proven separation in EntityCandidateService — to fetch bounded candidates from an entity's canonical source. No new pipeline stage is visible to ChatService, the router, the planner, or the runtime.

ContextFree-text references ("Women Gold Bangle Set") fail to match canonical row values ("Women's Gold Bangle Set") because no component today attempts row-level identity resolution before SQL is planned — proven in the prior investigation.
ScopeEvery enterprise entity type, every tenant, every domain — not a product feature.
Non-goalsNo fuzzy SQL, embeddings, or vector search. No new runtime layer. No second semantic pipeline. No new conversation-state model.
§1

Define the capability

One new concept, placed precisely against the three that already exist.

Grounding kindWhat it answersCardinalityOwner today
Business Object / AttributeWhat does "Product" mean, structurally?One per concept, tenant-wideAgent Brain
Enumerated Value DomainWhat are the legal values of a coded column?Small, closed, enum-sourcedAgent Brain via BLR
Business Reference newWhich specific row does the user mean?Open, row-level, unboundedUnowned today

Business Reference Resolution is the act of mapping a user-supplied surface string that names one instance of a Business Object — not the concept "Product," but the specific row "Women's Gold Bangle Set" — to its canonical enterprise value, before that value is allowed to become a SQL literal. It sits one level below Enumerated Value Domains on the same axis (both ground a literal against a persisted, authoritative set of values) and one level above them in cardinality: a value domain is closed and small by construction (an ENUM); a business reference is open and large (a product catalog, a supplier list, an employee roster).

It is not a new grounding category so much as the missing rung on a ladder that already has two rungs: object-level meaning, then attribute-level legal values. Business Reference Resolution is instance-level identity — the same ladder, one rung further down, toward the data.

§4

Candidate retrieval contract

Generic in, generic out — mirrors EntityCandidateService's existing "retrieves and renders; never decides" contract, one level down (row values, not entity concepts).

Input (generic)MeaningExample for this entity
Entity TypeWhich registered business concept is in playProduct
Canonical SourceThe one authoritative table for that conceptretail_core.products
Identity AttributeThe column that uniquely identifies a rowproducts.id
Display AttributeThe column a human recognizes the row byproducts.name
User ReferenceThe surface string from the question"Women Gold Bangle Set"
Output (generic)MeaningExplicitly excluded
Candidate listBounded set of {identity value, display value} pairsNo ranking score, no "best match" flag, no free-text explanation

The contract never names Products, Suppliers, or Stores — it is parameterized entirely by the four metadata fields in §3 plus the raw reference string. The same contract shape serves every entity type in every tenant because nothing about it is retail-shaped; it is shaped by BusinessEntity + AttributeRole, which already are.

What it must never do, stated as plainly as the existing precedent states it: rank candidates, choose among them, or infer a match. Those are Agent Brain's job (§5) — exactly the same separation EntityCandidateService's own Javadoc already draws between its retrieval and "the reuse-vs-create judgment [that] stays with the AI."

§5

Agent Brain: three cases

Agent Brain consumes the candidate list. It never retrieves; retrieval never judges.

Case A — one obvious candidate

Exactly one candidate, or one candidate whose display value normalizes (via the same deterministic normalization BusinessLanguageResolver already applies — lowercase, separator-insensitive, singular/plural) to an exact match against the user reference. Agent Brain accepts it and continues resolving — no different in kind from how it already accepts a single first-match-wins BusinessLanguageResolver resolution today. Investigation proceeds automatically; nothing downstream is aware a reference needed resolving at all.

Case B — several plausible candidates

Reuses the existing ASK_CLARIFICATION path rather than inventing a second one. The precedent already exists in ExecutionContract.isEmpty() — "True when no business object resolved — the agent may execute nothing" — a pre-planning short-circuit check ChatService already performs on Agent Brain's output before planning starts. An ambiguous reference is the same shape of check: Agent Brain's resolution result carries the candidate set; ChatService's existing branch (the same one that renders a router-originated clarification question today) renders it identically. The only change is where the clarification originates — from Agent Brain's resolution outcome as well as from the router's upfront classification — never a new rendering path, a new decision type surfaced to the user, or a second clarification subsystem.

Case C — no candidates

Zero candidates returned. Agent Brain does not invent a literal — it records, in the same reasoning trace it already produces, that no canonical match was found, and the resolution proceeds exactly as it does today for any other unresolved term: the user's original phrasing reaches the planner unchanged, annotate-never-substitute, with the honest absence of a resolution visible in the trace rather than silently masked. This mirrors the existing "zero-cost fallback" principle already documented on ResolvedQuestion — an empty resolution behaves byte-identically to no resolution attempt at all, it does not fail closed.

§6

Conversation continuity

"When did we last reorder it?" needs no new state — the carried-forward evidence mechanism already ships this.

A resolved canonical entity does not need its own conversation-state concept. The turn that resolves "Women Gold Bangle Set" → "Women's Gold Bangle Set" already produces query rows that get persisted as this turn's ExecutionReference — the same durable, per-turn record the existing follow-up mechanism already seeds the next turn's evidence from. A follow-up referring to "it" arrives with that prior turn's resolved entity and its retrieved data already present in the carried-forward evidence and conversation history text the planner already reads. Nothing about Business Reference Resolution requires a dedicated place to "remember" what was resolved — the conversation already remembers every turn's result, and a resolved reference is just one more fact inside that result.

§9

Architecture validation

Point-by-point proof, each tied to the mechanism that prevents the violation — not an assertion.

ConstraintProof
No duplicate reasoningResolution happens once, inside AgentBrain.resolve(), the same single call that already produces ResolvedBusinessModel. No second reasoning surface exists to duplicate.
No runtime business decisionsThe retrieval contract's only output is a bounded candidate list (§4) — structurally incapable of expressing a decision, mirroring EntityCandidateService's identical existing non-deciding shape.
No planner reasoningReasoningPlanner's prompt contract is untouched — it still only consumes a RESOLUTIONS line and copies a value, exactly as it does today for every other resolution kind.
No SQL semantic logicLiteralValidator and SqlGovernancePipeline are not touched by this design; resolution completes before any SQL is authored.
No tenant-specific behaviorThe contract (§4) is parameterized entirely by BusinessEntity/AttributeRole fields every tenant's metadata already carries in its own shape — nothing in the design names a tenant, an industry, or a table.
No feature-specific code path§8 traces five unrelated entity types through one unmodified sequence; none required a distinct branch.
Agent Brain sole owner of semantic reasoningEvery judgment call (Cases A/B/C, §5) is made inside Agent Brain; the retrieval component performs none.
ExecutionContract remains the governed boundary§2's sequence shows resolution completing strictly before ExecutionContractBuilder.compile() — the contract's shape and role are unchanged.
