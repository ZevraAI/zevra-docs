Planner Reasoning Specification — Textual Business References

How the existing Planner should reason about free-text business attributes when writing SQL, and the regression matrix used to validate that reasoning before any new architecture is considered.

Revision note

This revision applies exactly the five corrections from the preceding architecture review: Principle 4 rewritten to intent rather than mechanism; the regression matrix regraded on business outcome rather than SQL strategy; an explicit Non-Goals section added; former Principle 5 relocated to Limitations, since it documents a boundary rather than a rule the Planner follows; and three boundary clarifications added to resolve named under-specification. No new principle, capability, or architecture is introduced.

Scope

What this is, and isn't

This is a reasoning contract for the Planner's existing prompt — a statement of principles the prompt should encode, not new wording to paste in and not a new component. It governs one narrow question: given a free-text business attribute and a user's reference to it, when should the Planner filter with exact equality, when should it filter with partial matching, and when should it decline to assume its own guess is correct. It does not touch Agent Brain, the Evaluator, Runtime, or any metadata model.

Limitations

This is a boundary statement, not a Planner rule

Everything in this specification improves the construction of a filter. Nothing in it gives the Planner a way to verify that construction against real data. A partial-match filter, however well-reasoned, remains a guess about intent — better shaped, never confirmed. The Planner has no channel to know, in advance, whether zero, one, or several real rows will match. This limitation is unconditional: it applies to every principle below, including the ones that resolve the demonstrated inconsistency. Nothing in this document should be read as closing that gap — that determination belongs to the earlier architecture investigation's boundary between reasoning-solvable and capability-requiring problems, not to this specification.

Non-goals

Question classes intentionally out of scope

Not because these are unsolvable — because this specification is scoped to one thing (matching strategy for a single reference against a single column) and should not be read as silently covering more than that.

  • Aggregation over a multi-row match. When a partial match returns more than one row and the question aggregates ("total sales of bangle products"), how those rows should be combined is not addressed here.
  • Negation and exclusion. "Contains X but not Y" is not addressed.
  • Explicit multi-value enumeration. "Either Supplier A or Supplier B," naming multiple values of the same reference type, is a different shape than the multiple-different-entity-types case this specification does cover.
  • Multi-hop, nested reference resolution. Chains of joins where a reference at one hop depends on resolving a reference at another are not addressed.
  • Column-targeting ambiguity. When a term could plausibly refer to either an enumerated/coded column (already governed, unchanged) or a free-text column, which one the Planner should check, or whether it should check both, is not addressed.
§1

Reasoning principles

Principle 0 — the one that fixes the demonstrated inconsistency

Matching strategy is a property of the column, not the question. Today, the same reference ("bangle") produced different SQL depending on whether the surrounding sentence read as a browse request or a lookup request. That's backwards. Whether a filter should be exact or partial must be decided by what kind of attribute is being filtered — a free-text name/description versus a coded identifier — never by the grammatical shape of the sentence around it. The same reference, against the same column, must be reasoned about the same way regardless of how the question happens to be phrased.

Principle 1 — default posture for free text

For any attribute that is a human-authored name, title, or description (not a coded or enumerated value), treat the user's phrase as evidence of intent, not a guarantee of exact stored spelling. The default assumption is that punctuation, spacing, capitalization, and word form may differ between what the user typed and what is stored — not that they match.

Principle 2 — when exact equality is appropriate

Exact equality is appropriate only when there is independent reason to trust the literal is already canonical: it came from a resolved RESOLUTIONS or LITERAL CANDIDATES entry (unchanged, existing mechanism), or it is shaped like an identifier or code the user is clearly quoting verbatim — an invoice number, a PO number, a SKU, a promotion code, a store number. A number or a short alphanumeric code is being supplied as a code, not described in language, and should be matched as one — tolerant of surrounding punctuation (a leading "#"), but not of a wrong digit.

Principle 3 — when partial matching is appropriate

Partial matching is the default for any free-text, unconfirmed reference — not the exception reached for only when a query "feels" like browsing. This includes category fragments, full-name paraphrases, and anything without independent confirmation of exact spelling.

Principle 4 — tolerate formatting differences, not just spelling differences

A stored value may differ from the user's phrasing in punctuation, spacing, or minor formatting without differing in meaning. The Planner should not require a reference to match a stored value across its entire length to recognize they refer to the same thing — an incidental difference somewhere in the phrase should not, by itself, prevent a correct match. This is a statement of intent, not a matching technique: it does not prescribe how that tolerance is achieved, only that it is expected.

Principle 5 — this does not touch what already works

Columns with an existing legal-values list (RESOLUTIONS, LITERAL CANDIDATES) are already governed, already deterministic, and already correct. This specification fills the gap for columns that have neither — it does not modify or duplicate the existing enum-column behavior.

Boundary clarifications

Not new principles — resolving specific edge cases the six principles above leave undecided.

When both strategies would succeed

If a user's phrase already matches a stored value exactly, a tolerant filter still finds it — exact presence trivially satisfies a tolerant match. Behavior should not depend on the user coincidentally using perfect spelling: for an unconfirmed free-text column, apply the same tolerant posture regardless of whether the given phrase happens to look exact. Consistency, not precision, is what makes this predictable.

Mixed identifier + descriptive references

A reference is not always purely one or the other — "Invoice 12345 Customer Copy" contains both a code and descriptive words. Classify each part of a reference independently rather than forcing the whole phrase into a single bucket: the code-shaped portion follows Principle 2, the descriptive portion follows Principle 1/3.

Intentionally broad references

A tolerant filter matching many rows is not evidence the reasoning was wrong — breadth can be a property of the data, not a mistake in the query. The Planner is not expected to judge whether a given term is "too generic" before filtering; it is expected to apply the same posture consistently and let the actual result — one row, several, or none — speak for itself.

§2

Quick reference

Exact Use exact equality when…

  • The literal came from RESOLUTIONS or LITERAL CANDIDATES
  • The reference is purely numeric or code-shaped (invoice #, PO #, SKU, promo code, store/warehouse code)
  • The user is clearly quoting an identifier, not describing something in language

Tolerant Filter tolerantly when…

  • The attribute is a free-text name, title, or description
  • No legal-values list confirms the exact spelling
  • The reference is a category fragment, paraphrase, or full name typed from memory
  • Regardless of whether the question reads as a browse or a lookup

§4

Validation plan

  1. Baseline first. Run all 58 scenarios against the Planner exactly as it exists today, before any prompt change, and record the actual generated SQL and business outcome for each. This is the control — without it, "the prompt fixed it" can't be distinguished from "it happened to already work."
  2. Agree the reasoning contract. This document, §1, is that agreement — reviewed and settled before any prompt wording changes.
  3. Apply the principles to the Planner prompt. Out of scope for this document, per your instruction — happens only after step 2 is agreed.
  4. Re-run all 58 scenarios. Groups A–G (50 scenarios) are the actual bar: every one should now produce the correct business outcome — the right row, the right set, or, for scenario 5, a correctly returned multi-row set — regardless of which SQL mechanism the Planner used to get there. Group H (8 scenarios) is expected to still show the same unresolved outcome as baseline — if any Group H scenario starts passing, that's worth understanding on its own, not assuming as a bonus win; if any Group A–G scenario still fails, that's a real gap in the reasoning contract, not evidence the contract is insufficient in principle.
  5. Only after that comparison is complete, evaluate whether anything remaining in Group H — and only Group H — justifies new architecture, per the boundary already established.

Final consistency review

Re-verified against this revision, not carried forward by assumption.

  • Reasoning moved out of the Planner? No — every principle, including the three boundary clarifications, is content for the Planner's own prompt. Nothing added in this revision introduces a decision-maker elsewhere.
  • Runtime decisions introduced? No — Runtime is not mentioned; the outcome-based regression grading (§3) changes what is measured, not what Runtime does with the SQL it receives.
  • Agent Brain changes required? No — RESOLUTIONS and LITERAL CANDIDATES remain referenced only as existing, unmodified inputs.
  • Metadata evolution required? No — the Limitations section makes explicit that this specification does not close the gap requiring a metadata-backed capability; it does not introduce one either.
  • ExecutionContract changes required? No — not implicated by anything added or changed in this revision.
  • ReasoningEngine changes required? No — loop control, evidence handling, and evaluator behavior are not referenced.
