Enterprise Business Reference Grounding

Decomposition of the approved architecture into independently shippable, independently testable stories. Every constraint below is treated as fixed — this document allocates work against it, it does not revisit it.

§0

Implementation stories

Story 1

Restore Canonical Entity Metadata

Owner: Metadata
Objective

Give each canonical business entity a designated type, canonical source, identity attribute, and display attribute, using only fields that already exist today or existed prior to a later schema rebuild — curated the same way and at the same stage every other piece of semantic metadata already is.

Business value

Unlocks every later story. Without it, retrieval and Agent Brain have nothing concrete to act on — and because it's generic across entity types from the start, no per-type work is needed later.

Metadata governance — added on review

Entity Type, Canonical Source, Identity Attribute, and Display Attribute are curated metadata, not discovered metadata — the same category of work as the synonyms, descriptions, and object/attribute designations already curated today during onboarding, and owned by the same process. This story explicitly extends the existing onboarding curation responsibility to cover four more fields on an entity already being onboarded; it does not create a second curation process, a separate metadata workflow, or any automatic inference. No runtime component discovers, guesses, or infers these designations — a business object simply does not participate in grounding until a curator has set them, exactly as an object today does not participate in Business Language Resolution until it is curated into the domain.

Scope
  • Restore entity_type on BusinessEntity
  • Designate one existing IDENTIFIER-role attribute and one existing ATTRIBUTE-role attribute per participating object as its identity/display pair
  • Extend the existing onboarding curation activity to capture these four fields alongside the object/attribute curation it already performs
Out of scope
  • Retrieval logic
  • Agent Brain changes
  • New AttributeRole values
  • Backfilling data for existing entity rows
  • Any automatic discovery or inference of these designations
  • Any new curation workflow separate from existing onboarding
Components affected

Business entity metadata, and the existing onboarding curation activity that already populates it.

Architectural invariants

No new metadata model; AttributeRole's taxonomy stays closed; no new curation process — the same one process, extended; fully additive — an object without this designation is provably unaffected by everything that follows.

Risks

Semantic: mis-designating the wrong attribute as "display" silently produces wrong resolutions downstream — this story's correctness is foundational, not cosmetic. No architectural or backward-compatibility risk; purely additive.

Definition of done

Every object intended to participate in grounding has all four designations, set through the existing curation activity; objects without them are demonstrably untouched by the capability; no code path infers a designation automatically.

Regression tests

Existing consumers of entity/attribute metadata (BLR's indexing, prompt rendering) behave identically for objects that don't opt in.

Story 2

Deterministic Candidate Retrieval

Owner: Runtime — execution only
Ownership clarification — reviewed

"Executes through the existing governed SQL path" does not mean Runtime authors SQL. Candidate retrieval has exactly one fixed query shape, defined once, never composed or varied per question: select the identity and display attributes from the canonical source, filtered by the display attribute against the reference, bounded. Story 1's four metadata fields and the user's reference string only ever substitute values into that unchanging shape — they never choose a different shape. Runtime's contribution is exactly what it already provides for any other query: governance, safety, and audit of something handed to it. Runtime does not decide what to ask, does not compose novel SQL, and is not a second SQL-generation path alongside the Planner's LLM-driven one. If a future change to this story ever requires the query's shape to vary by entity type, by tenant, or by judgment, that is no longer this story — it is SQL authorship, and belongs nowhere in Runtime.

Objective

Provide deterministic candidate retrieval: entity type, canonical source, identity attribute, display attribute, and a user reference in; a bounded list of identity/display pairs out — nothing else. The one fixed query shape is executed through Runtime's existing governed execution capability, as a new caller of that capability, not a new execution mechanism and not a new authorship role.

Business value

The mechanical half of the capability. Generic by construction, so it serves every entity type — Product, Supplier, Store, Invoice, Employee — without type-specific work.

Scope
  • The single fixed, parameterized retrieval shape
  • Executed via the existing governed execution path (SELECT-only, safety-checked, audited identically to any other query)
Out of scope
  • Ranking or scoring
  • Any decision logic
  • Any variation of the query's shape — per entity type, per tenant, or otherwise
  • Any call site from Agent Brain (Story 3)
Components affected

None of the ten frozen components change. This is a new, small caller of the existing governed execution path — the path's own responsibility is unchanged, and Runtime gains no new kind of responsibility, only a new caller.

Architectural invariants

"Retrieval only, never chooses, never ranks" is enforced structurally — the return shape is incapable of carrying a score or a verdict. Runtime never becomes another semantic or SQL author — enforced by the query having exactly one shape, never composed. SQL Governance Pipeline unchanged, exercised identically.

Risks

Architectural — the risk this review exists to name: if implementation lets the query's shape vary (e.g. "just this once, branch the WHERE clause for invoices"), Runtime quietly becomes a second SQL author. Mitigated by treating any request to vary the shape as out of scope for this story, full stop, not as an extension of it. Runtime: candidate queries need the same row-limit/timeout discipline every governed query already has — no new class of runtime risk.

Definition of done

Given Story 1's metadata for any entity type, retrieval returns a correct bounded list for a match, an empty list for no match, runs through the existing governance chain identically to any other query, and does so through the single fixed query shape with no per-call variation — independently of Agent Brain.

Regression tests

Governance-pipeline coverage confirming this call is safety-checked like any other; a hand-rolled-fake unit test confirming the method's return shape cannot express a ranking or a decision; a test asserting the query shape itself is identical across different entity-type inputs, varying only in substituted values.

Story 3

Agent Brain Grounding Step

Owner: Agent Brain
Objective

Inside AgentBrain.resolve(), immediately after its existing BusinessLanguageResolver.resolve() call, invoke Story 2's retrieval for BLR-unresolved terms tied to a groundable object, and decide resolved / clarification required / no match — writing the outcome into ResolvedQuestion's existing resolution and unresolved-term channels, unchanged in shape.

Business value

The story that actually fixes the original defect. Everything before it is plumbing; everything after it is reuse and visibility.

Scope
  • The retrieval call
  • The three-way judgment
  • Writing the outcome into ResolvedQuestion's existing shape — a new ENTITY-kind resolution for a match, the existing unresolved/candidate channel otherwise
Out of scope
  • BusinessLanguageResolver's own matching logic
  • ExecutionContractBuilder, PromptContextBuilder, ReasoningPlanner, GovernedSqlRuntime, EvidenceStore
  • Clarification rendering (Story 4) and frontend display (Story 5)
Components affected

Agent Brain only.

Architectural invariants

Sole semantic-reasoning owner — this is the only place any judgment happens. Single semantic artifact — ResolvedBusinessModel's shape is unchanged. Planner stays unaware — it reads the same RESOLUTIONS block, sometimes with one more line.

Risks

Architectural / semantic — the highest-risk story in the roadmap. This is the only place a judgment call happens; getting the Case A acceptance threshold wrong (auto-accepting an ambiguous match) directly reintroduces a version of the original defect. No backward-compatibility risk for any object lacking Story 1's metadata — grounding simply never triggers. No new runtime risk beyond Story 2's.

Definition of done

Strengthened on review — every point below is a separate, independently checkable guarantee, not one combined statement:

  • Agent Brain is the only component that reads a candidate list and produces resolved / clarification required / no match — no other component in the roadmap makes this decision, and none is given the means to.
  • A candidate list with more than one entry never auto-resolves under any input — this is provable as a standing property of the decision logic, not just true for the test cases exercised.
  • Every ambiguous outcome routes through clarification (Story 4's path) — there is no third option between "resolved" and "clarification required" for a multi-candidate result.
  • An object carrying none of Story 1's four designations produces byte-identical behavior to today — grounding does not partially engage, does not attempt, and leaves no trace for such an object.
  • Planner's input shape is unchanged except for one additional standard ENTITY-kind resolution line in the RESOLUTIONS block it already parses — no new block, no new field, no new instruction added to the planner's prompt contract.
Regression tests

The same hand-rolled-fake pattern already used for the reasoning loop's own regression coverage — a fake retrieval collaborator scripted to return one / several / none candidates, asserting the resulting ResolvedQuestion shape for each; a dedicated end-to-end replay of the "Women Gold Bangle Set" scenario at the Agent Brain level.

Story 4

Reuse Clarification Rendering

Owner: ChatService
Objective

When Agent Brain's resolution signals clarification required (Case B), route it through ChatService's existing terminal-outcome and clarification-rendering path — the same family of pre-planning check ExecutionContract.isEmpty() already performs — triggered one step earlier than today's router-only trigger.

Business value

Turns Story 3's judgment into something the user actually sees, using zero new UI or response shape.

Scope

One additional pre-planning check in ChatService, same family as an existing one.

Out of scope

No new decision type beyond the existing clarification path; no router prompt changes; no new response field.

Components affected

ChatService only.

Architectural invariants

No new conversation state, no second clarification subsystem — the exact existing rendering is reused, not duplicated.

Risks

Lowest-risk story in the roadmap. No architectural, backward-compatibility, semantic, or runtime risk of note — ChatService makes no judgment here, only routes one Agent Brain already made.

Definition of done

A Case B resolution produces a user experience identical in shape to today's router-originated clarification.

Regression tests

Existing clarification tests pass unmodified, proving no change to the router-originated path; one new test confirming the Agent-Brain-originated trigger renders identically.

Story 5

Business Understanding Rendering

Owner: Frontend
Objective

Extend the Business Understanding section's existing resolution-rendering logic so a Business Reference resolution displays with the same fidelity every other resolution kind already has, including a provenance note when the resolution followed a clarification.

Business value

Closes the loop on trust — the user sees exactly what Zevra understood "Women Gold Bangle Set" to mean, using a surface that already exists and is already familiar.

Scope

One additional case in the section's existing source/rationale mapping logic.

Out of scope

No changes to the reasoning-trace component; no changes to the clarification question UI itself (Story 4's concern); no new feedback categories.

Components affected

The Business Understanding section only.

Architectural invariants

Transparency stays inside the one existing surface — no second transparency mechanism.

Risks

No architectural, backward-compatibility, or runtime risk — frontend-only, additive. A mislabeled provenance note is a cosmetic risk; the underlying data is already correct by the time it reaches this story.

Definition of done

A resolved business reference renders with user reference, resolved entity, confidence, and reason; a clarification-derived resolution additionally shows that provenance.

Regression tests

Existing resolution rendering for every other kind verified unchanged; new coverage for the reference-resolution case.

Story 6

Conversation Continuity Validation

Owner: Validation only
Objective

Confirm — without modifying anything — that the already-shipped evidence-carry-forward mechanism correctly carries a resolved business reference into a follow-up turn ("when did we last reorder it?").

Business value

Proves the capability is complete without inventing new state, exactly as required.

Scope

Test-only. A two-turn conversation: resolve a reference, then ask a follow-up referring back to it.

Out of scope

Any new persistence, conversation field, or cache — explicitly excluded by the frozen constraints, and this story exists to prove none is needed.

Components affected

None, by design.

Architectural invariants

No new conversation state, no new execution artifact, no new cache.

Risks

The one place this roadmap should pause rather than improvise: if validation finds the resolved entity's canonical value doesn't survive clearly enough into the persisted evidence for a follow-up to reuse it, that is a finding to bring back to the architecture conversation — not something to patch quietly inside this story.

Definition of done

The two-turn scenario demonstrably reuses the resolution with zero components touched.

Regression tests

Extends the existing follow-up continuation regression fixture with a business-reference-bearing seed step.

§6

Migration strategy

Metadata evolution is additive only: restoring entity_type and designating identity/display attributes (Story 1) requires no backfill of existing rows and no schema change to anything currently in use. An object that is never given these designations simply never triggers grounding — its behavior today is its behavior after every story in this roadmap ships. There is no cutover, no big-bang migration, and no tenant-wide rollout requirement: which objects participate in grounding is a data-curation decision made incrementally, object by object, domain by domain, entirely independent of deployment. Every existing tenant continues working unchanged the moment this ships, and gains the capability only where its own metadata is deliberately extended to support it.
