01What is Zevra?

Source: zevra-docs/docs/architecture-review/01-product-vision.md

Business framing

Zevra is positioned as an Executive AI Chief of Staff: a system that continuously watches an organization's operational data, investigates what changes, decides what matters, and briefs leadership in plain language — the way a human chief of staff would, but running every day, on every domain, without being asked.

Technical framing

Two front doors share one investigative engine: a scheduled Executive Brief pipeline (MorningBriefScheduler → MorningBriefService) and an on-demand Investigation Workspace (ChatController → ChatService). Both ultimately route through the same Agent Brain, execution contract, and governed SQL runtime described in Section 3.

What Zevra explicitly is not, per its own product-vision document

Not a BI dashboard. "A BI dashboard shows what its builder anticipated... Adding a new question means someone building a new tile, chart, or report — a development task, not a conversation." Zevra investigates each question fresh against live data; there is no fixed set of pre-built views.

Not a general AI chatbot. "A general-purpose AI chatbot is fluent but ungrounded... it cannot tell the difference between a real finding and a well-phrased guess." Zevra's answers are produced by actually querying live data — never generated from what a model believes is likely to be true.

Read-only by design. "Zevra never writes to an organization's operational systems... This is a deliberate product boundary," not a current limitation.

02Core Philosophy: Where Judgment Lives, and Where It Ends

A three-stage "Thinking → Understanding → Judgment" pipeline is not a documented or implemented concept anywhere in this codebase — it does not appear in the architecture-review corpus or in any class name. Per the zero-assumption rule, it is not used here. What is real, and does the same explanatory job, is the platform's actual reasoning/compile/execute/compose separation, described explicitly in docs/architecture-review/09-agent-architecture.md as the platform's "single hardest problem: keeping the model's judgment from becoming the last word on what executes."

Substitution made under the zero-assumption rule The requested "Thinking → Understanding → Judgment" framing has been replaced below with the real, verifiable pipeline. The underlying idea the requester wanted — that judgment is where the product's value lives, and that judgment is deliberately fenced off from execution — is real and documented; it is just expressed differently in the actual system.
1. Business Reasoning AgentBrain.resolve()LLM-influenced

What happens: The question is resolved into a ResolvedBusinessModel — which business objects and attributes are actually implicated — via EnterpriseSemanticAssembler and BusinessLanguageResolver. This is where the system decides what the question means.

↓
2. Deterministic Compilation ExecutionContractBuilder.compile()No LLM, no repository access

What happens: The resolved model is compiled into an immutable ExecutionContract (approved assets, semantic view, execution bindings, semantic hash). Verified in code: its only collaborator is SqlTableReferenceExtractor — "performs no business reasoning and accesses no repository." This is the boundary where judgment stops and a fixed, checkable artifact begins.

↓
3. Governed Execution SqlGovernancePipelineDeterministic gates

What happens: SQL — however it was authored — is checked against the contract's approved surface, then run through safety, data-contract, row-level-security, masking, routing, and audit stages. No model involvement. Detailed in Section 9.

↓
4. Response Composition NaturalLanguageComposer.compose()LLM

What happens: Query results are turned into a business-judgment answer — this is the single shared composition mechanic used by Chat, the Executive Brief, Reports, and Alerts (per docs/architecture-review/13).

Why judgment is the value

Anyone can run a query. The value Zevra sells is the interpretation: is this number good or bad, does it matter, what should a leader do about it. That interpretive step is inherently a model's job — no deterministic system can tell you whether a 4% inventory drop is a problem.

Why judgment is fenced off from execution

If the same model that exercises judgment also had unconstrained authority over what runs against production data, a hallucinated table name or an over-broad query becomes a live incident. ExecutionContractBuilder and SqlGovernancePipeline exist specifically so the model's judgment can be wrong, loud, or creative without that ever translating into an unsafe or unauthorized execution.

The one nuance worth stating precisely SQL generation is LLM-authored, not LLM-validated. There is no fixed SQL template and no whitelist of pre-approved queries — the model freely writes a SELECT statement. Safety comes entirely from the deterministic gate chain in Section 9 running after the model writes it, never from constraining what it's allowed to write in the first place.

06Agent Architecture

Two separate Agent systems coexist in this codebase A legacy, versioned construct — nexus_agent / AgentVersion / AgentPlaybook / AgentKpi — and the current runtime, nexus_zevra_agent / ZevraAgent / AgentRunner. They are not the same thing and should not be conflated. This walkthrough describes the current runtime.

Business framing

A Zevra Agent is a persistent, named investigator with a persona and a goal (e.g. "Inventory Watcher") that can be run on demand or scheduled, and that only ever looks at data sources it's explicitly allowed to see.

Technical framing

ZevraAgent (table nexus_zevra_agent): persona, goal, connection_keys[] allow-list, max_iterations, status (DRAFT/ACTIVE/ARCHIVED). Execution is driven by AgentRunner, producing a ZevraSession (table nexus_zevra_session, FK → nexus_zevra_agent) with a JSONB step trace and final output.

Two separate "session" concepts — do not conflate The conversational pipeline's ReasoningSession (table nexus_reasoning_session, FK → nexus_run) is a distinct construct from an agent's own ZevraSession (table nexus_zevra_session, FK → nexus_zevra_agent). Both are real; they are not the same table, and there is no foreign key joining them.
How they actually relate (verified, not the idealized chain) There is no formal, database-enforced object graph tying Agent → ReasoningSession → Finding → ExecutiveBrief together. What exists instead is several adjacent subsystems — Zevra Agents, conversational ReasoningSessions, OperationalFinding records, and the Morning Brief — that the frontend (HomePageMapper.ts) independently sources and stitches into one homepage experience. Implementation not found for a single unifying chain.
Agent registration

An operator defines a ZevraAgent: persona, goal, connection allow-list, iteration cap. Persisted to nexus_zevra_agent.

↓
Agent execution — AgentRunnerLLM tool-calling loop

Runs a ReAct-style loop: the model selects a tool (a SQL query against an allow-listed connection), the tool executes, the result feeds the next reasoning step, up to max_iterations.

↓

Every tool call is checked against the agent's connection allow-list (set-membership, deterministic) before the same governed SQL runtime described in Section 9 executes it.

↓

Only two write paths exist, both in ChatService (persistAgentFinding, persistInvestigationOutcome) — no separate anomaly-detection write path was found.

↓

A narrower, separate construct, nexus_investigation_recipe/_step, exists for recipe-driven templates but is not the general mechanism the frontend surfaces.

07Executive Brief

Business framing

Every tenant configures a time (e.g. 07:00, tenant-local timezone) for their brief to be ready. Leadership opens the homepage and sees a headline, a narrative, and links into supporting analysis — written in a deliberately terse, "Goldman Sachs morning note" tone.

Technical framing

MorningBriefScheduler is a @Scheduled(fixedDelay = 60_000) job — it polls every 60 seconds, it is not a cron expression — checking each tenant's MorningBriefConfig for a due brief.

1. Scheduler tick — MorningBriefScheduler.checkDueBriefs()

Every 60 seconds, loads all enabled tenant configs (MorningBriefRepository.findAllEnabledConfigs()), sets TenantContext per tenant.

↓
2. Due check — generateIfDue()

Compares the tenant's configured scheduleTime/timezone to current time; skips if today's brief already exists.

↓
3. Agent execution — AgentRunner.run() per active agentLLM

Runs each active agent (respecting an optional brief_agent_ids allow-list) against a fixed BRIEF_QUESTION_TEMPLATE: "Run exactly 3 queries, then call final_answer." Iterations capped at min(agent.maxIterations, 5).

↓
4. Result extraction — extractQueryResults()

Pulls raw SQL and result rows out of each agent's session.stepsJson(), not just narrative text — giving the synthesis step concrete numbers.

↓
5. Synthesis — NaturalLanguageComposer.compose()LLM, single call

System prompt explicitly instructs: "Never invent numbers. Use only what agents explicitly found," "Zero counts ARE data." Produces strict JSON: headline, sections[], agents_used[].

↓
6. Persistence — MorningBriefRepository.updateBriefReady()

Writes to nexus_morning_brief: headline, sections_json (JSONB), agents_used, status (READY/FAILED/GENERATING). A stuck brief auto-fails after 10 minutes in GENERATING.

↓
7. Homepage projection — HomePageMapper.tsFrontend

Self-documented in code as "a PURE transformation of existing backend records... no invented facts, no fabricated 'verified' counts." Maps the brief into the hero executiveSummary, and separately maps raw sessions/findings/anomalies/agents into KPI tiles and recommendation cards. Rendered by sei-nexus-ui/src/pages/Brief.jsx.

Documented but unconfirmed in code email_to exists as a column on nexus_morning_brief_config, but no delivery code was found for it. This matches the roadmap document's own claim that the Brief is "a UI-only surface today — deliberately distinct from Scheduled Reports, which do deliver externally." Treat email delivery of the Executive Brief as not implemented, not merely undocumented.

09Governance Layer

Verified classes in com.sei.nexus.governance: ExecutionContract, ExecutionContractBuilder (in agentbrain), ColumnPolicy, RlsPolicy, DataContract, DataContractService, AuditEvent, SqlGovernancePipeline (+ SqlGovernancePipelineTest), plus sql.SqlSafetyService, sql.SqlTableReferenceExtractor.

How SQL determinism actually works: generate-then-validate, not templates or whitelists The LLM freely authors a SELECT statement — there is no fixed template and no whitelist of pre-approved queries. Determinism comes entirely from a deterministic gate chain applied identically regardless of which reasoning path produced the SQL (conversational, agent, or brief).
1. Approved-surface check — ExecutionContract.approvedAssets

A precomputed, immutable set-membership check. SQL's referenced tables are extracted (SqlTableReferenceExtractor) and checked for membership. Unapproved → deterministic rejection and re-plan — never silently rewritten (verified in ChatService's contractGateMode=enforce handling).

↓
2. SQL safety — SqlSafetyService.validate()

Pure string/regex validation: must start with SELECT, no semicolons, no INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/TRUNCATE/EXEC/EXECUTE/MERGE/GRANT/REVOKE as whole words, no bare SELECT *.

↓
3. Data contracts — DataContractService

Tenant-configured column/query-level rules.

↓
4. Row-level security — RowLevelSecurityService

Per-user row filtering.

↓
5. Column masking — ColumnMaskingService

Sensitive value redaction.

↓
6. Routing, row limits, timeouts

Sync vs. async by cost; bounded execution — 100 rows / 30s timeout on the agent path, per autonomous-agents.md.

↓
7. Audit — GovernanceAuditService.recordOutcome()

Unconditional record of what ran, under which contract, for whom, with what outcome — regardless of success, rejection, or block.

This chain is shared, not path-specific The same SqlGovernancePipeline runs for the conversational path, the autonomous agent path, and the Executive Brief path (per ADR-0003 A2), confirmed by a real test — GovernanceParityIntegrationTest — asserting parity between agent and conversational governance outcomes.
